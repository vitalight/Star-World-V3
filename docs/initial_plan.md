# 第一阶段执行计划：开发者主界面与三个工作区

状态：2026-10-21 已完成实现与运行验证，Blueprint 待用户二选一，模块待独立评审。执行结果与环境说明见 [阶段交付记录](reviews/phase_one.md)。本文保留本阶段原始目标与验收范围。

## 目标与结构关系

先搭建开发者主界面，再完成其下的 Blueprint、Art Test 和 Logic Test。Game Test 本轮保留可进入的占位页面。

```text
开发者主界面（项目默认启动入口）
├── Blueprint              # 两个概念图版本，用户二选一
├── Art Test               # 使用 StarterContent 展示美术
│   ├── Character
│   ├── Effect
│   └── Battle Scene
├── Logic Test             # 极简平面 2D 战斗场景
└── Game Test              # 本轮占位，后续集成正式美术和逻辑
```

四个工作区是开发者主界面下的同级入口。Battle Scene 属于 Art Test，只展示美术；Game Test 用于后续实机集成，两者职责不同。

## 1. 开发者主界面

### 目标与范围

- 启动项目后首先显示开发者首页，有明确的 Blueprint、Art Test、Logic Test、Game Test 四个导航入口及简短用途说明。
- 点击入口进入对应工作区，每个工作区均能返回主界面。
- 显示当前工作区名称，让用户明确自己所在的位置。
- 主界面只负责导航和工作区承载，具体展示及战斗逻辑保留在各自模块中。
- 离开工作区后停止其动画或模拟活动，反复进入时不会产生重复实例、重复计时或后台战斗。
- Game Test 可以进入，并明确标注“待集成”，支持返回。

### 路径与验收

主入口沿用 `devtools/hub/developer_hub.tscn`，作为项目默认启动场景。
先完成首页 → 四个工作区 → 返回首页的导航闭环，再填充下列三个工作区。各工作区保留独立运行能力，独立运行时也应能正常使用返回操作。

### 1.1 Blueprint：生成两个版本的概念图

**目标**：使用 imagegen 生成两个不同方向的塔防战斗概念图，交给用户二选一。

工作内容：

- 阅读 ArtReference，两个方案都以其为主要视觉目标；允许后续替换 StarterContent，不受其画风限制。
- 生成 A、B 两个版本，包含地图、我方角色、敌人、攻击特效及战斗 UI。
- 保持用途和画面范围可比较，在场景氛围、地形构成或视觉布局上形成明显区别，避免仅改变颜色。
- 在 Blueprint 中完整展示两张图片，标明 A / B，并提供简短方向说明。
- 保留两份原图和生成提示词，等待用户选择；不替用户确定最终方案。

产物：

- 展示入口：`devtools/blueprint/blueprint_workspace.tscn`。
- 图片：`devtools/blueprint/images/`。
- 提示词与版本说明：`devtools/blueprint/`。

验收：两张概念图可查看、差异清晰，能辨认塔防战场、双方单位和主要 UI。交付至“待用户二选一”即可，不阻塞 Art Test 和 Logic Test。
概念图是整体视觉参考，本轮不要求将其切分为正式资产；A / B 版本标签不是正式内容 ID。

### 1.2 Art Test：使用 StarterContent 搭建美术展示关卡

**目标**：把现有素材做成可检查的美术展示，不等待概念图选择。后续允许按选定方案替换素材。

先查看 `Human/StarterContent/character/`、`effects/`、`texture/` 图集，再确定切片和可用动画，不凭文件名假定帧数和动作。

工作内容：

- **Character**：至少展示一个我方角色和一个敌人，支持分别检查并播放素材中实际可用的动画，标注当前内容与动作。
- **Effect**：至少展示一个现有图集中的特效，支持重复播放。
- **Battle Scene**：使用现有地形纹理搭建小型战场，摆放双方单位与示例特效，加入简单静态战斗 UI，检查比例、位置、遮挡和画面关系。
- 三类展示均可从 Art Test 进入，并具有可以单独运行的展示场景。
- 使用模拟展示数据，不计算伤害、波次或胜负；记录素材缺失及其他限制。

产物：

- 入口与预览操作：`devtools/art_test/`，保留 `art_workspace.tscn` 入口。
- 可复用表现能力：`features/actor_view/`、`features/effects/`、`features/battlefield_view/`、`features/battle_hud/`，按实际需要实现。
- 整理后的具体资源：`content/`，按架构约定分配内容 ID。
- 操作说明、素材使用情况与限制：本工作区内。

验收：三个区域均可用，可检查角色、敌人、特效及包含静态 UI 的战场；独立于战斗模拟运行。保留 StarterContent 原始输入，不覆盖原件。

### 1.3 Logic Test：极简平面 2D 战斗场景

**目标**：用简单几何图形验证最小可玩的塔防战斗闭环，独立于正式美术。

视觉要求：俯视平面 2D，用矩形、圆形、线条、文字和颜色区分双方、道路、出生点、终点及可部署位置。不加载 StarterContent、概念图或 Art Test 表现资源。

工作内容：

1. 一个小型战场和一条固定敌人路径。
2. 一种可放置在指定位置的我方单位。
3. 一种沿路径移动的敌人，按一波测试配置生成。
4. 我方自动攻击范围内敌人，体现生命变化及敌人被消灭。
5. 敌人抵达终点造成生命损失；本波生成完毕且全部敌人处理完、生命尚存时胜利，生命耗尽时失败。
6. 提供开始、重置，以及生命和剩余敌人等必要状态显示。

只实现一种攻击方式和固定路径，数值用于验证流程。复杂技能、职业、多关卡和精细表现留到后续。

产物：

- 战斗规则：`features/battle/`。
- 占位显示、测试配置与调试操作：`devtools/logic_test/`，保留 `logic_workspace.tscn` 入口。
- 核心规则的针对性自动验证：`features/battle/tests/`。
- 操作说明与已知限制：本工作区内。

验收：可以放置单位并观察移动、攻击和消灭；胜利、失败均可验证，重置后能重新开始。验证部署合法性、伤害和胜负等关键行为。
规则与显示分开，便于后续复用；测试素材与临时场景留在工作区，本轮不占用 Art Test 整理的正式内容 ID。

### 1.4 Game Test：预留集成入口

保留 `devtools/game_test/game_workspace.tscn`。本轮提供可进入、可返回的占位页面，说明后续将组装经过评审的战斗模块与美术模块。本轮不实现实机集成。

## 2. 执行顺序与协作范围

1. 检查现有工程，完成开发者主界面的导航闭环，确定各工作区的进入和退出方式。
2. 主界面就绪后，Blueprint、Art Test、Logic Test 可并行推进，三者互不等待。可以委派并行子代理，各自负责对应工作区和上述产物目录。
3. 由主执行者维护主界面、项目配置和共享文档；子任务保持工作区入口路径稳定，不修改其他任务负责的文件。
4. 将三个工作区接入主界面，验证往返导航和重复进入。
5. 交付运行说明、检查结果、已知限制，以及两张待选择的概念图。

主界面的完成是子任务的共同前置条件。用户选图只影响后续正式美术方向，不影响本轮另外两个工作区的交付。

## 3. 整体验收与交付

- F5 启动进入开发者首页，四个入口和返回路径可用。
- Blueprint 有两个实际生成且可查看的方案，等待用户二选一。
- Art Test 的三类展示可用，使用现有 StarterContent。
- Logic Test 能运行并重置极简战斗，具有可验证的胜负流程。
- Game Test 清晰标注为待集成。
- 反复进入和离开工作区不会产生重复对象或后台模拟。
- 完成 Godot 资源导入与启动检查，并实际检查可见界面、动画、导航和战斗操作；将环境错误与项目错误分别记录。
- 提供操作方式和已知限制，完成模块评审记录后，再安排 Game Test 正式集成。

所有计划内功能应交付为可检查的结果；遇到环境或工具阻塞时明确记录未完成项，不将占位内容标记为已完成。
